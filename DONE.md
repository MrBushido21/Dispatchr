## DISP-1 · Привести проект в собираемое состояние

**Коммит:** `2e51d15` — `chore: clean deps, fix build, rename project`

**Зачем.** `npm run build` падал: `app.module.ts` импортировал `./auth/auth.module`,
которого не существовало. Плюс в зависимостях лежал форк-валидатор из прошлого
проекта, конфликтующий с обычным `class-validator`.

**Что сделано.**

1. `package.json` → `name`: `freelance` → `dispatchr`.
2. `npm rm @nestjs/class-validator` — форк-обёртка Nest поверх `class-validator`.
3. Проверена версия `typeorm`.
4. Поставлены зависимости фазы 0:
   ```
   npm i @nestjs/jwt @nestjs/passport passport passport-jwt argon2 \
         @nestjs/swagger @nestjs/terminus ioredis \
         nestjs-pino pino-http
   npm i -D @types/passport-jwt pino-pretty
   ```
   Отложено осознанно: `socket.io` + `@socket.io/redis-adapter` (фаза 1),
   `@aws-sdk/*` (фаза 2), `bullmq` + `web-push` (фаза 4),
   `@nestjs/throttler` + Prometheus (перед первым деплоем).
5. Сборка починена — импорт `AuthModule` удалён из `app.module.ts`
   (в тикете предлагалась пустая заглушка; удаление чище — модуль появится в DISP-5).
6. `.gitignore`: убрана строка `docs.md`, `.env*` заменено на `.env`.

**Итоги и заметки.**

- **`typeorm@1.0.0` — версия настоящая.** Подозрение не подтвердилось:
  `npm ls typeorm` показывает `@nestjs/typeorm@11.0.2 → typeorm@1.0.0 deduped`,
  то есть Nest резолвит её как свой peer. Фиксировать ничего не нужно.

- **В чём был конфликт `@nestjs/class-validator`** (уточнено по исходникам —
  первоначальное объяснение «разные реестры метаданных» неверно):
  оба пакета пишут в **одно и то же** глобальное хранилище
  `global.classValidatorMetadataStorage`. Проблемы две:
  1. форк заморожен на 0.13.4, канон на 0.15.1 — два писателя разных версий
     в одну структуру, поведение зависит от порядка импортов;
  2. `@nestjs/common/pipes/validation.pipe.js` жёстко делает
     `require('class-validator')` — `ValidationPipe` **физически не может**
     использовать форк, даже если DTO размечены его декораторами.

- В `devDependencies` заехали лишние `i@0.3.7` и `npm@11.19.0` (опечатка в команде
  установки) — удалены.

## DISP-2 · Инфраструктура в Docker: PostGIS + Redis + MinIO

**Коммит:** `b21a7d9` — `chore: postgis, redis and minio in docker-compose`

**Зачем.** Три внешних сервиса из архитектуры (`docs.md` §2), поднимаются одним
`docker compose up`, чтобы не переписывать compose на каждой фазе.

**Что сделано.**

1. Образ Postgres → `postgis/postgis:16-3.4`. Обычный `postgres:16-alpine` не
   содержит расширения, а тип `geography(Point,4326)` из `docs.md` §4 нужен уже
   в DISP-4 — без него не создаётся ни `orders`, ни `courier_positions`.
2. Добавлен `redis:7-alpine` со своим томом. Четыре роли: pub/sub между
   инстансами, GEO-индекс живых позиций, локи/идемпотентность, очереди BullMQ.
3. Добавлен MinIO: `9000` (S3 API) + `9001` (веб-консоль),
   `command: server /data --console-address ":9001"`.
4. Healthcheck на всех трёх сервисах.
5. `.env` приведён в порядок, создан `.env.example`.

**Итоги и заметки.**

- **Имена переменных задаёт entrypoint образа, а не его название.** Попытка
  переименовать `POSTGRES_DB` → `POSTGIS_DB` ломает старт: образ postgis собран
  поверх официального postgres и ищет строго `POSTGRES_*`.

- **Опечатка в пути тома тиха и опасна.** `/var/lib/postgisql/data` вместо
  `/var/lib/postgresql/data` — контейнер запустится и будет работать, но данные
  лягут в слой контейнера и исчезнут при `docker compose down`.

- **`$$` в healthcheck.** Compose подставляет `$VAR` из `.env` при разборе YAML.
  `$$` экранирует доллар, чтобы переменную развернул шелл **контейнера** из
  своего окружения — тогда проверка использует те креды, с которыми сервис
  реально запущен, а не те, что лежат в файле на машине.

- **`curl` в образе `minio/minio` есть** (`/usr/bin/curl`) — распространённое
  утверждение об обратном не подтвердилось. Проверка всё равно оставлена на
  `mc ready local`: родная утилита сервиса не зависит от состава образа.

- **Тайминги healthcheck.** Рабочий набор: `interval: 10s`, `timeout: 5s`,
  `retries: 5`, `start_period: 30s`. Жёсткое правило — `timeout < interval`.
  `start_period` нужен именно Postgres: первый запуск с initdb и установкой
  расширений занимает 10–30 секунд, и провалы в этом окне не должны считаться.

**Проверено фактически.**

```
docker compose ps        → три сервиса healthy
SELECT postgis_version() → 3.4 USE_GEOS=1 USE_PROJ=1 USE_STATS=1
\dx после down/up        → 5 расширений на месте, тома работают
git ls-files             → .env.example отслеживается, .env — нет
```

## Алгоритм, выведенный по ходу: healthcheck для любой технологии

Docker умеет ровно одно — запустить команду в контейнере и посмотреть код
возврата. `0` — здоров, всё остальное — провал. Значит задача всегда одна:
найти команду, которая внутри контейнера возвращает 0 при готовности сервиса.

0. **Проверь, нет ли готового:** `docker inspect --format='{{json .Config.Healthcheck}}' <образ>`
1. **Найди родной CLI:** `docker compose exec <сервис> sh`, затем `ls /usr/local/bin`.
   Ищи `<имя>-cli`, `<имя>admin`, `<имя>ctl` — у них обычно есть `ping`/`status`/`ready`.
2. **Прогони руками:** `docker compose exec <сервис> <команда>; echo $?`
3. **Проверь, что она умеет падать:** останови сервис и убедись, что код ≠ 0.
   Проверка, всегда возвращающая 0, хуже, чем её отсутствие.
4. **Перенеси в compose** с таймингами выше.

Запасной вариант, если родного CLI нет: `curl -f http://localhost:PORT/health`
(флаг `-f` обязателен — без него curl вернёт 0 даже на HTTP 500), в alpine —
`wget --spider -q`, в крайнем случае `echo > /dev/tcp/localhost/PORT`.
Утилита должна существовать **внутри** контейнера.
